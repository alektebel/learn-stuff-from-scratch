# MCP From Scratch

Build a Model Context Protocol server in pure standard-library Python, from the
bytes up: the JSON-RPC envelope and the codes the spec pins, the three transports
that frame it (a stdio line, an SSE event, an HTTP POST), the lifecycle handshake
with a capability table that cannot lie, tools whose errors are split into
protocol and execution, resources and prompt templates with the one "not found"
the spec distinguishes, subscriptions, progress and cancellation, a read-only
toolset with an allowlisted report in the middle, idempotency keys for a caller
that retries, a confirmation dialog that shows the diff it is about to apply, and
a trajectory policy with an audit line that carries no clock and no payload.

Pinned to the **2025-06-18** revision of the spec (`schema/2025-06-18/schema.json`).
Where the spec leaves a choice, the decision is written down in the template's
docstring as a DESIGN DECISION, and the check asserts the consequence.

An MCP server is not a framework. It is a message shape, a dispatcher, a session
and a policy — and the interesting failures are the ones a client cannot see:
a message that is not JSON, an id that cannot be answered, a log line on stdout
that corrupts the stream, a revision echoed back unchecked, a capability
declared but not implemented, an argument that never reached a tool, a cancelled
request answered anyway, a retry that created a second purchase order, an
approval replayed against a change nobody approved, and three individually safe
calls composing into an unsafe batch. Every one of those is a test here, not a
postmortem.

No sockets, no network, no wall clock: every transport reads and writes in-memory
streams, so a check can hand the server bytes and read exactly what came back.
The ERP the tools read and write is provided (`erp.py`) — the domain is not the
exercise, the protocol is.

## The stages

| # | File | The mechanism | The thing people get wrong |
|---|---|---|---|
| 1 | `stage_01.py` | The envelope, `Dispatcher`, the pinned codes | A null or boolean `id` accepted as a `RequestId`; an unknown *notification* answered; an invented error code; a JSON-RPC batch treated as a message |
| 2 | `stage_02.py` | `LineTransport`, `SseWriter`, `HttpTransport` | A log line on stdout; a frame split across chunks losing its tail; a `\r` left on the line; 200 instead of 202 for a notification POST |
| 3 | `stage_03.py` | `Server`, the handshake, capabilities | The client's revision echoed back unchecked; a request served before `initialized`; a capability declared with nothing behind it; `"elicitation": {}` read as "no" |
| 4 | `stage_04.py` | `Tool`, `ToolRegistry`, `text_result` | A schema violation answered as `isError`; an execution failure answered as -32602; `isError` omitted; `nextCursor: null` on the last page; `str(dict)` in the text |
| 5 | `stage_05.py` | `Resource`, `Prompt`, the two registries | An unknown URI answered -32602 — the one "not found" the spec pins at -32002; an unknown prompt name answered -32002; a loader run while looking a URI up |
| 6 | `stage_06.py` | `Subscriptions`, `Progress`, `Cancellations` | A cancelled request answered anyway (-32800 looks helpful and is unmatched); `requestId` read as `id`; progress that goes backwards; `initialize` cancellable |
| 7 | `stage_07.py` | `Toolset`, `Reports`, `make_tools` | A mutating tool *listed* while read-only; refused but its fn still run anyway; `enable_writes` with nobody's name on it; a filter value interpolated into the query |
| 8 | `stage_08.py` | `Ledger`, `CREATE_ORDER_SCHEMA` | The key optional, or generated by the server; a business failure not stored, so the retry re-attempts; a validation failure stored; the replay re-rendered instead of returned |
| 9 | `stage_09.py` | `diff_token`, `Confirmation`, `format_diff` | The dialog showing the arguments instead of the diff; a truthy string read as an approval; a token bound to the call instead of the state; the identity taken from the arguments |
| 10 | `stage_10.py` | `SessionPolicy`, `Audit`, `guard` | A cap that never fires; three safe calls composing past the ceiling; a stale approval accepted; a refusal answered as a protocol error; an audit line with a clock or a payload in it |

## How to use this directory

```bash
python3 codecraft/cli.py run mcp-from-scratch   # what to build next, and why
python3 codecraft/cli.py hint mcp-from-scratch  # when a nudge is not enough
```

Or without codecraft:

```bash
python3 -c "import course; [print(i, s.title) for i, s in enumerate(course.STAGES, 1)]"
```

Implement the templates at the top level; finished versions are in `solutions/`.
The stages are cumulative — stage 5 pages with stage 4's cursor dialect, stage 9
registers through stage 4's table, stage 10 wraps stage 3's dispatcher — so a
check for a late stage needs the earlier ones implemented, and `solutions/`
overlaid on the templates is the state those checks are written against.

## Prerequisites

Standard library only: `json`, `hashlib`, `copy`, `os`. No `mcp`, no
`pydantic`, no HTTP client, no SDK. You should be comfortable with dicts,
classes, `try/except` and `json.dumps(..., sort_keys=True)`; everything else —
the framing, the handshake, the registries, the ledger, the policy — is built
here.

## Design decisions

- **The domain is provided; the protocol is the exercise.** `erp.py` is a small
  read/write model with business rules that say no (an unknown vendor, a
  duplicate reference, a non-positive quantity). Stages 7-9 are about what a
  server does *with* a failure, and a course that also asks you to write the
  ERP would bury that.
- **A tool is not a method.** Tools live in one table (`server.tools`) and are
  reached only through `tools/call`. A server that exposes `create_purchase_order`
  as a JSON-RPC method has made `tools/list` decorative and told every client
  its tool names in advance.
- **A schema violation means the call never happened; a failure inside the tool
  means it happened and did not work.** The first is -32602 (`data: {"tool": …}`),
  the second is an ordinary result with `isError: true`. Getting this backwards
  is the most common MCP server bug, and it is invisible until a model has to
  decide whether to retry.
- **There is exactly one "not found" the spec pins: a resource URI, -32002 with
  `data.uri`.** An unknown prompt name, an unknown report name and a bad cursor
  are invalid params, because a prompt and a report are not addressable by URI
  and a cursor is a position the server handed out. Inventing a code for the
  others makes a client's error handling guesswork.
- **A cancelled request gets no response at all.** The spec says not to send one;
  a `-32800` is a message the client that already gave up cannot match. The rule
  lives in one place (`Cancellations.answer_for`) so the server's dispatcher can
  consult it and a check can prove it.
- **Read-only first, and mean it.** In read-only mode a mutating tool is not
  merely refused when called: it is not *listed*. A tool the model can see is a
  tool the model will call, and every call it makes costs a turn. The flag lives
  on the SERVER (`server.read_only` starts true), so a stage that registers a
  tool takes effect at the door instead of being one more thing the switch has to
  remember; flipping it needs a named approver, and the flip is only
  half-announced if nobody sends `notifications/tools/list_changed`.
- **The report tool is the workable middle.** One tool with an allowlist of
  report names, an allowlist of filter columns per report and a declared type per
  column — somewhere between one `run_query(sql)` and fifty narrow tools. Column
  names come from the schema and values travel as data, so a value cannot be
  anything but a value.
- **An idempotency key is an argument, and it is required.** A server-generated
  key dedupes nothing, because the retry brings a different one. A business
  failure consumes the key (the attempt happened); a validation failure does not
  (it never reached the tool). The retry of a stored outcome returns the same
  bytes, or the client can tell the two calls apart and the point is lost.
- **The confirmation shows the diff, not the tool call.** A dialog that reads
  `apply_change({"quantity": 25})` tells a person what the agent wanted; the
  dialog has to say `change quantity from 10 to 25`. The approval is then bound to
  that diff (`sha256` of the canonical diff), so a token issued for one state
  cannot authorise another — which is the difference between a confirmation and
  authorisation.
- **The identity comes from the session, never from the arguments.** A tool that
  declares an `identity` parameter lets a caller claim to be someone else. The
  identity is on the session (in a real deployment it arrives with the OAuth
  token at the transport); a tool's `inputSchema` does not have the word in it,
  and `tools/call` refuses it as an undeclared argument.
- **Safety is a property of the sequence.** Three calls that move 40 units each
  are individually fine and together move 120. The policy keeps a window of
  writes with a cap and an aggregate ceiling; a person's approval shows the whole
  batch and resets the window; and *any* write makes every earlier approval stale,
  because an approval describes a state and a write ends that state.
- **A policy refusal is an execution outcome, not a protocol error.** "You may
  not do that" is something the MODEL has to act on: it reads results, not error
  codes. So a refused call answers an ordinary `isError: true` result, and the
  one thing that is asserted is that the tool's fn did not run.
- **Reads are never refused.** A session that cannot read cannot explain itself,
  and refusing reads is how a budget stops the agent from telling a person what
  it already did.
- **The audit line has no clock and no payload.** One deterministic line per
  message: method, id, ok, error code, identity, mutations. A wall clock makes the
  log untestable and unmergeable; a copied payload is a second copy of the
  customer's data in the one place nobody guards. Both are asserted twice: the key
  set is exact, and a secret-shaped filter value is proven absent from the line.
- **No sockets.** `LineTransport` is newline-delimited framing over any pair of
  file-like objects, `SseWriter` produces the event text, and `HttpTransport.post`
  returns `(status, content_type, body)`. That is what makes stdout purity — the
  rule that the server MUST NOT write anything to stdout that is not a valid MCP
  message — a thing a check can prove rather than a hope.

## Verification

The solutions pass all ten checks, and every check is mutation-tested: **120
plausible wrong implementations** — a null id accepted, a batch parsed as a
message, an unknown notification answered, a crashing handler reported as
invalid params, a log line on stdout, a chunk boundary losing the tail, `\r\n`
unhandled, 200 for a notification POST, an unchecked revision, a request served
before `initialized`, capabilities read from the declaration, a duplicate tool
silently replacing a definition, an unknown tool answered as `isError`, a
`ToolError` raised as a protocol error, `nextCursor: null`, `str(value)` in the
text, an unknown URI answered -32602, a prompt name answered -32002, a loader run
during a lookup, a cancelled request answered with -32800, `requestId` read as
`id`, a boolean progress token, a mutating tool listed while read-only, a refused
tool still run, `enable_writes` with an empty approver, a filter value
interpolated into the query, the key made optional, a server-generated key, a
business failure not stored, a validation failure stored, a re-rendered replay,
the dialog showing the arguments, a truthy string as an approval, a token bound
to the call, the identity taken from the arguments, a cap that never fires, an
unchecked aggregate, a stale approval accepted, a read refused, a business
failure spending the window, a refusal answered as a protocol error, an audit line
with a clock, an audit line with the params in it — are each planted into a
solution, and the stage's check must fail. Every assertion message names the
read as `isError`, a list served while the note that would answer it is lost, a
disabled definition published without the reason it is disabled, the flip
releasing only its own tools, a change's quantity never counted against the
window — each one planted in a copy of the solutions and caught, and every
message names the mistake, not the symptom.

Two more proofs sit outside the per-stage checks: `mutate_all.py` plants the
other seven stages' mutations against the assembled course (`MISSED OR BROKEN:
0`), and a smoke run drives an eighteen-message conversation — handshake, reads,
the attributed flip, an idempotent retry, three confirmation rounds, the
aggregate refusal, a self-cancelling request — through all ten stages composed,
on one wire, with the audit's shape asserted at the end.

```bash
python3 codecraft/cli.py run mcp-from-scratch   # per stage, with the failure line
```

## Where this stops

Deliberately left out, so you know the boundary:

- **No sockets, no server.** The transports frame bytes for a stream you provide.
  TLS, HTTP parsing, SSE resumability (`Last-Event-ID`), keep-alive and
  backpressure are the deployment's job.
- **No real subprocess.** The stdio framing is exact; spawning a child, draining
  two pipes and killing it on a timeout is process management, and it is not the
  part that breaks a protocol.
- **No authorisation system.** The identity is a string on the session. Whether
  it comes from an OAuth token, a service account or a header, and what it is
  allowed to do, is an identity question this course names and does not solve.
- **No client-side features.** Sampling, roots, logging and the full
  `elicitation/create` schema are sketched or absent; the confirmation flow here
  is the one whose server side is worth designing.
- **One pinned revision.** 2025-06-18 only: no revision negotiation across
  several, no compatibility shims, no features that landed after it.
- **One cursor dialect.** Opaque `str(offset)` cursors over a registration-order
  list, with the key absent at the end. Real servers page a database and have to
  make the cursor survive an insert; the invariant — a missing `nextCursor` is the
  end — is what this course pins.
- **Single-threaded.** A cancelled request is a *policy* ("send no response"), not
  a thread kill; nothing here preempts a tool that is already running, which is
  why the progress token and the cancellation registry are separate concerns.
- **The ERP is dictionaries.** No SQL, no transactions, no locking. The point is
  that a change has a `diff()` a person can read and an `apply()` that validates
  what it is handed.
